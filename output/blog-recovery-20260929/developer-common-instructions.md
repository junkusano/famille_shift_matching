# MyFamille 共通開発・本番公開ルール

対象：MyFamille（famille-shift-matching / myfamille.shi-on.net）。独立した別製品のリポジトリをこの設定に変更しない。

## 各開発者のパーソナライズへ貼り付ける共通指示

あなたはMyFamilleの共同開発者です。自分の変更だけでなく、他の開発者の修正と現在の本番機能を保持してください。以下を共通ルールとします。

1. 正規の共有リポジトリは https://github.com/junkusano/famille_shift_matching 、本番用ブランチは master とする。Vercelの対象は famille-shift-matching、本番URLは https://myfamille.shi-on.net 。ローカルのフォルダ名や「Already up to date」だけで接続先の正しさを判断しない。GitとVercelの接続先が異なる場合は本番公開を止め、差異を報告して設定を統一する。
2. 作業開始時は、現在のブランチ、未コミット変更、originのURLを確認し、originをfetchする。他人または別タスクの変更を消さない。既存変更は内容を確認して安全に保存・分離する。古い作業ブランチを次の仕事に使い回さず、最新origin/masterからcodex/で始まる作業ブランチを作成する。
3. 変更はその作業ブランチにcommitし、同じブランチへpushする。作業ブランチから本番へ直接Deployしない。masterへの直接pushも通常運用にしない。PRで対象差分・既存機能への影響・検証結果を確認し、必要な承認とチェックを経てmasterへ統合する。
4. pull、push、Deployを区別する。pullは取得と統合、pushは共有リポジトリへの保存、Deployは本番アプリ全体の切替である。自分が編集していない機能も、古い版をDeployすれば戻り得る。「変更箇所しか反映されない」と考えない。
5. 競合や警告を無視しない。一括して自分側・相手側を採用せず、双方の変更意図を確認して統合する。git reset --hard、git clean、強制pushで警告を消さない。どの変更を残すか不明な場合は、差分と影響を示して確認する。改行警告と、未保存変更の消失・競合・履歴分岐を区別する。
6. Deployは、共有masterに統合済みの特定コミットから、未コミット変更のない専用チェックアウトまたはCIで行う。対象コミット、現在の本番Deploy ID、その元コミット、Vercelのプロジェクト・環境を記録する。現在の本番にある変更が候補へ含まれていない場合は公開せず、先に統合する。意図的なロールバックは別途明示的に承認された場合だけ行う。
7. 変更に必要なテストと本番ビルドを通す。型チェック等に既存エラーがある場合は、修正前後を比較して新規エラーの有無を記録し、全件成功と報告しない。未検証・失敗・除外した範囲を明示する。
8. 本番への反映は同時に行わず、CIの公開待ち行列または共有の公開担当を通して直列化する。公開直前に本番Deploy IDを再取得する。準備中に本番が変わっていたら、そのまま昇格させず最新版との統合・再検証を行う。
9. Deploy後は、本番URLが意図したDeploy IDを参照し、定期実行も同じ版を参照していること、対象機能が実際に動くことを確認する。管理画面・DB・外部公開結果など、機能に適した確認を行う。READYやHTTP 200だけで機能修復を断定しない。検証のためだけに通知・送金・外部投稿を重複実行しない。
10. 緊急修正も原則として同じ経路で共有masterへ保存してから公開する。緊急時の例外が明示的に承認された場合は、公開した差分を速やかにmasterへ戻し、統合完了まで次の通常Deployを行わない。本番だけ・ローカルだけに修正を残さない。
11. 完了報告には、変更内容、共有リポジトリとコミット、Deploy ID、実施した検証、未解決事項を記す。手元だけ修正した状態、pushだけ完了した状態、本番まで確認した状態を区別する。
12. 認証情報、環境変数の値、利用者・職員情報をGit、PR、ログ、報告文へ出さない。必要な設定は既存の秘密情報管理を使用する。

## 各開発者が導入時に必ず実施すること

- 自分の作業フォルダのorigin、現在のブランチ、未コミット変更、未pushコミットを点検し、結果を共有する。
- 古い作業ブランチや本番専用の修正を棚卸しする。必要な変更をPRでmasterに統合し、履歴を消して帳尻を合わせない。
- 全員が同じ正規リポジトリ・masterを基準にしていることを確認し、この共通指示を各自のパーソナライズへ登録する。
- Vercelへ直接本番Deployする個人のスクリプト、作業フォルダ、GitHub Actions、Deploy Hook等を確認して申告する。公開経路を一つに決めるまでは、各自の判断で別経路から本番へ出さない。

## 管理者・公開担当が一度だけ実施すること

- VercelのGit連携先を正規リポジトリと本番用masterへ統一する。2026-09-29の確認時点ではservicesuport-dot/cm-rpaへの旧連携が残っている。差分と現在本番を保全してから切り替える。本書作成時点では設定未変更。
- 古いGit連携、Deploy Hook、CIから同じ本番を更新する経路を整理する。不要と確認できた経路を停止する。
- masterにPR・必要なテストを要求し、通常の強制push・直接pushを制限する。緊急例外の担当と手順も決める。
- 本番Deployを一つのCIまたは公開担当に集約し、同時公開を防ぐ。一般の開発作業ではPreviewだけを利用する。
- 本番コミット・Deploy ID・公開日時・確認結果を、全員が参照できる場所へ残す。

## 毎回の必須作業

| 時点 | 必須事項 |
| --- | --- |
| 作業開始 | status・ブランチ・origin確認、fetch、最新masterから作業ブランチ作成 |
| 共有 | 対象変更だけcommit、作業ブランチへpush、PRで差分と検証結果を共有 |
| 統合 | 他の変更を保持して競合解消、テスト、masterへ統合 |
| 公開前 | masterのコミット指定、クリーンなビルド、現在本番との差分確認、公開を直列化 |
| 公開後 | 本番とcronの参照先、対象機能の動作、コミット・Deploy IDを記録 |

設定の変更と、この文章を配布することは別作業である。文章を登録しただけで、Vercelの旧連携や各自の直接公開経路が自動的に解消されるわけではない。
