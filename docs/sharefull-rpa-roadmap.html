現在位置

完了: Sharefull RPAの基本機能テンプレート作成、案件掲載、クローズの基本ジョブとRunner連携。
完了: テスト用テーブルの分離本番テーブルとSharefullテスト用テーブルを分離。
完了: テスト用Vercelプロジェクト作成テストURL、テスト用環境変数、専用Runnerを利用。
現在ここ テンプレート作成 → 案件掲載 → 応募・応募確定通知 → クローズの段階検証Google Apps ScriptがGmailを取得し、テストAPIへapplied／confirmedを登録した後、テスト用LINE WORKSへ通知する経路を確認する。
次: 実運用に近い案件で確認認証設定、状態更新、重複防止・失敗時再試行・送信先分離を確認してから本番用GASへ移行する。

本番とテストの境界

本番

通常運用

本番MyFamille、本番テーブル、タイミーPAD、本番cronを利用します。

テスト

Sharefullと応募通知を確認

別URLのテストVercel、テスト用テーブル、テスト用Gmail、テスト用GAS、テスト用LINE WORKSグループを使用します。

共有

rpa_runner_jobs

現状は本番とテストで共有されるため、専用Runnerを使わない初回テストでは安全条件を守ります。

初回テスト開始前の必須条件: 本番の pending ジョブ0件 → 本番の claimed ジョブ0件 → 本番cron停止 → テスト用Gmail／LINE WORKS送信先を確認 → テスト実行 → 終了後に未完了ジョブと本番テーブルの状態を確認。

テストの進め方

1単体テスト関数・ジョブ登録の確認
2テンプレート作成だけ審査中までの作成経路
3案件掲載だけ審査完了テンプレートから掲載
4応募・応募確定通知だけGmail → GAS → テストAPI → LINE WORKS、状態更新・重複除外
5クローズだけID照合と不一致時の中止
6通しテスト作成 → 掲載 → 応募通知 → クローズ
7実運用に近い1件本番移行前の最終確認

応募通知のテスト構成

工程テスト用構成
受信Sharefull応募通知 → テスト用Gmailラベル
取得・判定時間主導トリガーのGoogle Apps Script。送信元・件名・求人ID・管理番号・応募者・状態を検証
登録・状態更新テストAPIへappliedまたはconfirmedを送信し、同じ応募識別キーを更新
重複防止GmailメッセージIDと応募識別キーを処理済みキーとして保存
通知テスト用LINE WORKSグループのみ。実行ログに成功・失敗・再試行を記録
本番移行条件: テスト用送信先で一度だけ通知されること、再実行で二重通知されないこと、API失敗時に再試行・失敗記録が残ることを確認してから、本番用GASと本番LINE WORKS送信先へ切り替えます。

タイミーPADの段階的な置き換え

Chrome RPAを別ジョブ種別で実装既存PAD経路を維持したまま追加
テスト案件で検証専用テーブルまたは対象案件を使用
並行稼働PADとChrome RPAを比較
1利用者・1案件単位で切替失敗時はPADへ戻す
全件切替安定確認後にPAD停止
