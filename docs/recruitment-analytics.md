# 応募導線分析

ナレッジ活用自動化の `recruitment-analytics` テンプレートで登録する。初期設定は月曜09:00 JST、保存のみ。`/portal/recruitment-analytics` は応募者管理のエントリー一覧の下に配置する。

## 集計と保存

- 前週月曜〜日曜と前々週を比較する。DB件数はJSTの半開区間で集計する。
- 有効なGA4情報源から、ホスト付きページ別表示・利用者、エントリーページの参照元、公開ページの端末別指標を取得する。同じプロパティIDは一度だけ取得する。
- MyFamilleは公開LPと `/entry` に限定。氏名、連絡先、応募本文、個別の応募レコードは取得せず、`form_entries` の新規登録件数のみ読む。再応募の送信件数やLP別帰属ではない。
- GA4対象行なし、API失敗、上位行制限、しきい値・サンプリング・タイムゾーン差を明記する。DB応募件数÷GA4ページ表示を応募率としない。
- Clarityは既存の保存済み集計を参照。重なる3日スナップショットを合算しない。日次07:35 JSTの `/api/cron/knowledge-analytics-sync` がGA4/Clarityを独立取得し、遅い一般情報源による取りこぼしを防ぐ。
- 関連するアクセス・採用ナレッジを照合する。報告と改善案は `knowledge_items` の `recruitment_analytics_report` に一体で保存する。週開始日をキーにし、再実行・競合でも重複作成しない。
- レポートは内部限定、AI作成・要確認。改善案は仮説であり確定方針ではない。ナレッジ管理で確認・編集でき、次週の分析で参照する。
- レポートAPIはmanager/adminのみ。集計の欠損は失敗や警告として表示し、欠損を0にしない。

## 外部処理

分析生成は既存OpenAI APIを使用する。送信するものは集計値・公開ページURL・個人情報なしの関連ナレッジ要約。OpenAIレスポンスの保存は無効 (`store:false`)。2026-10-11にユーザーから外部送信の明示承認を得た。

既存のブログリライトは、人が確認・承認したレポートを候補選定の参考として参照する。内部数値や応募情報を検索クエリ・公開記事に含めない。週次レポート作成が公開記事の自動変更を直接開始することはない。

公開ページの変更やLINE WORKSへの通知は、このタスクでは行わない。

# 2026-10-15 改善

- 週次評価は Responses API の strict JSON Schema で形式・文字数・改善案件数を指定。未完了・本文なし・形式不正は保存せず、レポート専用の安全な診断を表示する。
- GA4 / Clarity の集計に加え、自サイトの段階別計測を併記。LP表示、応募ボタン（上部・下部・本文）、入力開始、入力エラー、送信操作、送信エラー、新規登録成功、既存応募者の確認依頼を区別する。
- `recruitment_journey_events` はサービスロールだけが読み書きする。氏名・メール・入力値・応募ID・IP・任意URLを保存しない。30分のブラウザ内識別子による仮名化データであり、個人情報から完全匿名と断定しない。日次同期で180日以前を削除する。
- 公開エンドポイントでは新規登録成功を受け付けない。成功は応募登録APIの確認後に記録する。計測失敗・1500ms超過は応募を失敗扱いにしない。既存応募者を新規応募に含めない。
- 同じ段階・ページ・ボタン位置はブラウザ識別子ごとに重複排除。異なる位置の件数を足して人数にしない。観測件数は厳密な順序付きファネル・実人数・送信試行総数ではない。流入元はリンク/参照元の手掛かり。GA4人数と合算しない。導入前の欠測は復元不可。
- MyFamilleは `/` と `/entry` にだけ計測部品を設置。管理画面では動かない。施恩側は採用LPのみ、`scripts/recruitment-wordpress-tracking.cjs` の dry-runで差分確認し、公開済みスクリプトを確認後に `--apply` で既存本文を保全して導入。既存GA4/Clarity設定は変更しない。
- 応募フォームは連打防止、同一内容の通信再試行で同じ登録キーを使用。既に登録済みのキーで成功を返した場合は通知を再送しない。テストはDB/通知を模擬し、実応募・通知は生成しない。
